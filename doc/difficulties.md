# 当前系统的难点与应对策略（Top Selling Intelligence Demo）

> 本文专门总结：在“TikTok Shop vs Shopee Top Selling Intelligence”Demo 场景下，最容易翻车/最耗时间的难点是什么，以及 Demo 级与上线级分别怎么应对。

## 1. 难点总览（按优先级）

1. **数据获取不稳定**（反爬、字段变动、站点差异）
2. **proxy 口径不一致**（两平台“热销”信号不可比）
3. **标准化最吃业务细节**（品牌别名、规格单位、套装/多件装）
4. **跨平台 matching 天然歧义**（同名不同物、同物不同名、变体/套装）
5. **“可执行洞察”需要可解释**（否则很难被定价/品类团队采纳）
6. **扩展到千万级的思路要讲得通**（不做全量但要有路径）

7. **合规与数据治理容易被忽略**（ToS/隐私/血缘/审计）

8. **高性能架构带来工程复杂度与成本**（组件多、运维重、SLO 约束）

---

## 2. 难点细化与解决思路

### 2.1 数据获取（Ingestion）

**难点**

- 平台反爬/频控导致请求失败、封禁或数据缺失。
- 页面结构与字段频繁变化，脚本易碎。
- TikTok Shop 与 Shopee 不同国家站点字段差异大（币种、税费、促销展示）。

**Demo 级应对**

- 以“可重复跑通”为优先：
  - 只抓 1–2 个品类 + Top N（例如 200）
  - 把 raw 响应落盘缓存（按 platform/category/date）
  - 失败时允许使用 stub 数据（文档说明哪些是 stub）
- 设计成“多 source 适配”：同一表字段可以来自不同抓取路径/第三方数据。

**上线级应对**

- 明确数据来源优先级：官方 API / 第三方数据 / 自研抓取。
- 加入可靠性机制：
  - 任务队列 + 重试/退避 + 熔断
  - 代理池/UA 轮换（合规前提下）
  - 监控与报警（成功率、字段缺失率）

---

### 2.2 Top selling proxy 的可比性

**难点**

- 两个平台的“sold / GMV / rank / reviews / likes”等字段含义不同，时间口径不同。
- 有的字段可能只有区间或累计值，难以形成同口径对比。

**Demo 级应对**

- 把 proxy 设计成可插拔：统一落到 `sales_proxy(proxy_type, proxy_value)`。
- 在文档明确：
  - 本次主 proxy 是什么（例如 rank + review_count）
  - 偏差来源
  - 拿不到字段时的替代方案

**上线级应对**

- 为不同 proxy 定义“可信度等级”和适用场景。
- 对比逻辑尽量用“相对指标”替代“绝对可比”：
  - 同平台内趋势
  - 同类目/同品牌内排名

---

### 2.3 标准化（品牌/规格/单位/币种）

**难点**

- 品牌别名：同品牌不同写法（大小写、语言、缩写、店铺名混入）。
- 规格解析：标题中的容量/重量/件数格式多样；还有“套装/组合装/赠品”。
- 单位换算：ml/L、g/kg、pcs/pack 等。

**Demo 级应对**

- 先做“可解释的规则系统”，再补字典：
  - 规格：regex 提取数值 + 单位 + 简单容忍区间
  - 品牌：手工字典（几十个以内）+ 规则清洗（去噪词）
- 对“套装/多件装”明确处理策略：
  - 识别 `2pcs/3x/pack` → 记录 `pack_count`（可选）
  - Demo 先按“总量/单件”二选一统一（必须写进文档）

**上线级应对**

- 建立可维护的标准化资产：品牌别名表、规格解析规则版本化、人工 override。

---

### 2.4 跨平台 matching（同款/同类）

**难点**

- 同名不同物：标题相似但实际规格/版本不同。
- 同物不同名：TikTok 强营销标题 vs Shopee 偏参数标题。
- 变体/套装导致“同款”的业务定义不一致。

**Demo 级应对**

- 强制可解释输出：`match_type + confidence + reasons`。
- 采用“候选集召回 + 规则/相似度打分”的混合：
  - 强特征优先：品牌一致、规格接近
  - 弱特征补充：标题相似、类目一致、价格带一致
- 引入 review/override 流程：0.65–0.85 进入人工审核队列。

**上线级应对**

- 把人工审核变成闭环资产：覆盖更多品牌与规格，逐步提升自动接受率。

---

### 2.5 洞察/预警的“可执行性”

**难点**

- 仅有榜单/热度数据时，容易输出“看起来对但无法行动”的结论。
- 定价/品类团队需要的是：为什么、影响多大、下一步做什么。

**Demo 级应对**

- 每条 alert/opportunity 必须带：原因（reasons）+ 建议动作（action）。
- 机会清单用最小闭环：`our_status` + `notes`（允许 stub）。

**上线级应对**

- 接入我方库存/毛利/供应可得性/门店覆盖等信号，完善“可执行建议”。

---

### 2.6 扩展到千万级（不做全量但要讲清方案）

**难点**

- 题目不要求实现全量，但要求你说明“上线怎么扩”。

**Demo 级应对**

- 清晰表达策略：
  - 只抓热销候选集（类目榜单 + 关键词 top）
  - 增量更新（每天只更新变化项）
  - 缓存（raw/标准化/匹配结果）
  - 人审闭环（低置信度）

**上线级应对**

- 用队列与分层存储支撑规模化；把匹配拆成离线批处理 + 在线查证。

---

### 2.7 合规与数据治理（生产落地的硬门槛）

**难点**

- 采集是否符合平台 ToS/robots 与当地法规，容易在“PoC→上线”阶段成为阻断项。
- 缺乏数据血缘与审计会导致：
  - 结果不可追溯（为什么这条匹配/预警出现？）
  - 规则变更后无法解释历史差异

**Demo 级应对**

- 文档中明确：数据来源、抓取方式、限制条件与替代方案（官方/第三方）。
- 在数据表中保留最小追溯字段：`url/source`、`ingested_at`、`rule_version`（如果有）。

**上线级应对**

- 优先切换到合规数据源（官方/第三方）并建立访问控制。
- 建立 lineage：raw → standardised → matched/alerts 的可追溯链路。

---

### 2.8 工程复杂度与成本（高性能方案的代价）

**难点**

- Kafka/Iceberg/Spark/ClickHouse/OpenSearch/向量库等组件一旦齐全，部署、监控、升级与排障成本显著增加。
- 系统需要明确 SLO：
  - 数据延迟（T+? 小时/分钟）
  - 查询响应时间（P95）
  - 匹配准确率与人工审核量上限

**Demo 级应对**

- 仍以单机/单库跑通流程为主，但在文档里把“组件替换路径”写清。

**上线级应对**

- 用分层与解耦控制复杂度：
  - 采集/处理/服务分离
  - 批处理优先，只有明确需要时再引入流处理
- 做成本与收益评估：
  - 先覆盖 1–2 个高价值品类
  - 以人审闭环提升质量，而不是一开始追求全自动

---

## 3. 建议的验收方式（Demo 评审可用）

- 抽样人工评估 matching：随机抽 30–50 对，统计 exact/variant/similar 的准确率。
- 抽样评估 alerts：每类 alert 抽 5–10 条，看 reasons 是否自洽、动作是否合理。
- 对数据稳定性给出透明说明：哪些字段稳定、哪些是 stub、未来如何替换。
