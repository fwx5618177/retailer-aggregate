# Backend / Data Engineer — 面试评分表

## 使用方式

- 适用于 Backend / Data Engineer 岗位的 Round 1 / Round 2
- 每项按 1-5 分评分：1 = 明显不达标，2 = 偏弱，3 = 基本达标，4 = 明显胜任，5 = 超预期
- 建议总分门槛：$\ge 3.5 / 5$
- 以下项目中，`数据链路设计能力`、`AWS 架构判断能力` 不应低于 3 分

## 评分维度

| 维度             | 权重 | 核心判断                             |
| ---------------- | :--: | ------------------------------------ |
| 数据链路设计能力 | 25%  | 是否能设计从采集到查询的完整主链路   |
| AWS 架构判断能力 | 20%  | 是否真正理解服务边界、成本和运行模式 |
| SQL 与性能能力   | 20%  | 是否能优化查询、区分存储路径和热路径 |
| 故障排查与稳定性 | 20%  | 是否能结构化定位问题并降低 MTTR      |
| ownership 与沟通 | 15%  | 是否适合小团队独立推进               |

## 重点题目与观察点

### 题目 1：每日数据 pipeline 设计题

**题目：** 设计每日 pipeline：SFTP CSV (50MB) → 清洗 → S3 Parquet → SQL 可查询。选什么技术？怎么编排？怎么处理失败？

**重点观察：**

- 是否会按采集、清洗、落湖、查询、导出拆解
- 是否理解 Parquet、分区、元数据管理
- 是否考虑幂等、补数、重试、告警

**高分信号：**

- 明确区分 Bronze / Silver / Gold 或类似分层
- 知道为什么要用 Parquet、分区、Catalog
- 能讲清失败重跑、幂等和补数策略

**低分信号：**

- 只会泛泛说“写个脚本跑一下”
- 不理解数据格式和查询成本
- 没有恢复和告警设计

### 题目 2：Fargate / Service / Lambda 选型题

**题目：** Fargate Task vs Service vs Lambda，分别适用什么？日批 pipeline 用哪个？API 呢？

**重点观察：**

- 是否知道任务型与服务型负载的区别
- 是否理解执行时长、冷启动、运行模式、成本边界
- 是否能结合当前业务给合理选择

**高分信号：**

- 能说出批处理、常驻服务、事件触发的边界
- 会结合数据规模和团队阶段做判断
- 能给出“为什么不用另一个方案”的原因

**低分信号：**

- 背定义但不会套用到场景
- 只会说“都可以”
- 没有成本和可运维性意识

### 题目 3：PostgreSQL 查询优化题

**题目：** PostgreSQL 500 万行，按 platform + category + date 过滤 + price 排序 + 分页，P95 <1s，怎么做？

**重点观察：**

- 是否理解索引设计和执行计划
- 是否知道 offset 分页问题
- 是否能考虑读路径、缓存和数据切分

**高分信号：**

- 主动提到复合索引、执行计划、keyset pagination、缓存
- 知道查询字段和排序字段如何影响索引
- 会从接口和数据访问模式反推优化策略

**低分信号：**

- 只说“加索引”
- 不会解释为什么慢
- 不懂分页代价

### 题目 4：故障排查题

**题目：** Pipeline 02:30 失败，Step Functions 显示 Standardization 超时。怎么排查？

**重点观察：**

- 是否有清晰排查顺序
- 是否知道看日志、状态机、输入规模、下游依赖、权限/网络
- 是否能给短期修复和长期改进

**高分信号：**

- 先确认范围，再定位瓶颈，再提出缓解与修复
- 会讲监控、指标、超时边界、重试策略
- 能把事故转成系统优化项

**低分信号：**

- 直接说“重跑试试”
- 没有系统化步骤
- 只关注代码，不关注运行环境和依赖

## Red Flags

- 只做过脚本或局部接口，没有生产链路经验
- 不能解释为什么选某个 AWS 服务
- 没有 SQL 调优或慢查询处理经验
- 故障排查思路混乱
- 对成本、监控、稳定性没有基本意识
