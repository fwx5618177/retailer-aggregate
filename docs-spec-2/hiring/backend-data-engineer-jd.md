# Backend / Data Engineer — Pricing Center

## 职位概述

我们正在建设一个东南亚电商价格情报产品。系统会采集外部商品价格数据，完成标准化、匹配、告警和查询服务，并通过 Dashboard、API 和数据导出交付给客户。

该岗位负责把现有数据 pipeline 和 API 从本地 MVP 推进到 AWS 生产环境，确保链路稳定、成本可控、可持续演进。

## 你将负责

- 搭建和维护 AWS 生产基础设施，包括 ECS、S3、RDS、Athena、Step Functions、Cognito
- 打通第三方数据 → 数据湖 → 查询服务 → 客户导出的主链路
- 将现有 Python pipeline 与 Spring Boot API 适配到生产环境
- 负责 CI/CD、监控告警、基础安全、运行稳定性和故障排查
- 与 Tech Lead 一起推进数据契约、服务边界和性能优化

## 任职要求

### Must Have

- 4-6 年后端或数据工程经验
- 有 AWS ECS、S3、RDS 的真实生产经验
- 熟悉 Python 数据处理、批处理任务编排、数据落湖
- 熟悉 PostgreSQL，能做索引设计、分页优化、慢查询分析
- 能独立推进一个模块从设计到上线，而不是只做子任务实现

### Nice to Have

- 有 Step Functions / Airflow / Athena / Glue / Redshift 经验
- 能读改 Java / Spring Boot
- 有 ETL、零售、电商、定价或 BI 相关经验
- 熟悉 Parquet、分区设计、成本优化

- Terraform

## 我们更看重什么

- 能不能把“本地能跑”变成“生产可用”
- 能不能在控制复杂度和成本的前提下做合理设计
- 能不能独立排查故障并给出结构化解决方案
- 能不能理解数据链路、API 服务、基础设施三者的关系

## 面试会重点考察的具体内容

### 1. 数据链路设计能力

候选人需要能够回答：

- SFTP / API 数据如何可靠落到 S3
- 清洗后的数据为什么要用 Parquet、如何做分区
- 如何让 SQL 查询可用且成本可控
- 失败重试、幂等、补数、告警如何设计

**我们想看到的信号：**

- 会按链路拆解：采集、清洗、落湖、查询、导出
- 知道文件格式、分区、元数据管理对后续查询成本的影响
- 理解失败处理和可恢复性，而不是只讲“重跑”

### 2. AWS 架构判断能力

候选人需要能够回答：

- Fargate Task / Service / Lambda 的适用边界
- 为什么这个场景适合 Athena 而不是更重的数仓方案
- 什么时候该上托管服务，什么时候该自己管
- 如何在安全、成本、运维之间做平衡

**我们想看到的信号：**

- 知道服务边界和典型 trade-off
- 不是只会背 AWS 名词
- 会从实际数据规模和团队阶段做判断

### 3. SQL 与服务性能能力

候选人需要能够回答：

- PostgreSQL 大表过滤、排序、分页如何优化
- 哪些查询适合进 RDS，哪些适合进 Athena
- 热路径怎么做缓存或预计算
- 慢查询怎么定位、怎么改索引、怎么验证效果

**我们想看到的信号：**

- 有真实 SQL 调优经验
- 知道索引、执行计划、分页代价
- 能把查询路径和业务接口联系起来

### 4. 故障排查能力

候选人需要能够回答：

- 日批失败时先看什么、后看什么
- 超时、数据缺失、导出失败、权限错误怎么区分
- 如何减少 MTTR
- 如何把一次事故转成系统性改进

**我们想看到的信号：**

- 排查顺序清晰
- 会用日志、指标、状态机、依赖关系来定位问题
- 能提出长期改进而不是只会临时修补

## 不适合这个岗位的人

- 只有脚本或单机数据处理经验，缺少生产系统经验
- 只做过局部 API 开发，缺少基础设施和数据链路意识
- 对云成本、运行稳定性、故障排查没有概念
- 不适应 startup 的模糊需求和快速节奏
