# 0. 需求定义

> **文档版本**: 1.0.0
> **最后更新**: 2026-02-26
> **相关文档**: [scope/mvp-scope.md](../scope/mvp-scope.md) (v2.0)

## 问题陈述

东南亚电商平台上的畅销商品榜单日新月异。零售商和品牌需要实时洞察：
- **竞争格局**：我的产品在各平台的排名如何？
- **跨平台视角**：同一商品在 Shopee 和 TikTok Shop 上的表现差异是什么？
- **机会识别**：哪些高排名商品还未被我覆盖？
- **异常检测**：排名为何突然上升/下降？价格异常是否反映供应问题？

**现状**: 零售商手动跟踪多个平台、多个品类的商品排名，消耗大量人力，延迟高，覆盖面不全。

**目标**: 建立自动化情报流水线，**日采集、日标准化、日匹配、日告警**，为决策者提供即用型竞争洞察。

## MVP 需求范围

### 地理与市场范围

| 属性 | 值 |
|-----|---|
| **目标国家** | 泰国（TH） |
| **目标平台** | Shopee Thailand (`shopee.co.th`) + TikTok Shop Thailand (`tiktokshop.com` TH 区域) |
| **目标品类** | 个人护理（Personal Care）|
| **子品类** | 沐浴露、洗发水、护肤品（保湿霜、洁面乳、精华液） |
| **货币** | 泰铢（THB） |
| **时区** | Asia/Bangkok (UTC+7) |

**为什么是个人护理？**
- 品类定义清晰，产品特性相似（易于标准化）
- 平台上货物充足，排名变化频繁（有新闻价值）
- 品牌集中度高（易于匹配，高准确率）
- 符合泰国消费热点

### 数据范围

| 参数 | 默认值 | 可选值 | 说明 |
|-----|-------|-------|-----|
| **TopN** | 200 | 50-500 | 每平台每子品类的采集范围 |
| **分析窗口** | 14 天 | 7, 14, 30 天 | 趋势分析的时间范围 |
| **更新频率** | 每日 | 定时（02:00 UTC+7）| 批处理模式，非实时 |
| **数据保留** | 90+ 天 | — | 支持回放重处理 |

**数据量估算**:
- 采集：200 商品/平台 × 2 平台 × 3 子品类 = 1,200 个列表/天
- 标准化后：~400 个商品/日
- 跨平台匹配：~95 个配对/日（60% 匹配率）
- 告警：~20 条/日

### 核心功能需求

#### 1. 数据采集（Ingestion）

**FR-1.1 从 Shopee Thailand 采集商品列表**
- 数据源：Shopee 畅销排名页面 (`shopee.co.th/personal_care`)
- 字段：排名、商品 ID、标题、价格、评论数、销售代理、图片 URL
- 失败处理：HTTP 429 降速，403 轮换代理，5xx 指数退避，超时递增重试
- 状态追踪：通过 `batch_id` 和 `run_id` 关联每次采集运行

**FR-1.2 从 TikTok Shop Thailand 采集商品列表**
- 数据源：TikTok Shop 品类浏览页面
- 字段同上
- 限速控制：遵守平台 robots.txt 和 `Retry-After` 头
- 降级策略：无 API 时改用结构化抓取

**FR-1.3 支持存根数据模式**
- 本地开发默认使用 YAML 预生成的 200 个商品/平台（避免网络依赖）
- 生产环境实时抓取，失败时自动回退到存根数据
- 抓取失败通过告警通知

#### 2. 数据标准化（Standardization）

**FR-2.1 品牌归一化**
- 将 `brand_raw`（平台原始字符串）映射到标准品牌名 `brand_std`
- 包含别名字典（如 `NIVEA` ← [nivea, Nivea Men, NIVEA MEN]）
- 未知品牌使用 RapidFuzz 模糊匹配（相似度 > 0.8）
- 标准化缓存：LRU 缓存（max 10,000 条目），JSON 持久化

**FR-2.2 价格转换**
- 所有价格转换为 **satang**（泰铢最小单位，1 THB = 100 satang）
- 存储为整数，避免浮点精度问题
- 支持列表价和促销价两个字段

**FR-2.3 规格提取**
- 从标题中提取数值规格（如 "500ml"、"200g"）
- 输出：`size_value` + `size_unit` + `normalized_ml` / `normalized_g`
- 支持多包检测（如 "3-pack"）

**FR-2.4 单价计算**
- 计算 `price_per_ml` 和 `price_per_g`，用于跨商品比较
- 支持不同单位的规范化（ml ↔ L，g ↔ kg）

#### 3. 数据质量保证（Data Quality）

**FR-3.1 16 项 DQ 检查**
- 字段缺失率、异常值、排名唯一性、价格范围、货币一致性等
- 三级响应：**阻断**（完全失败）/ **降级**（继续但标记警告）/ **警告**（日志记录）

**FR-3.2 DQ 状态传播**
- DQ 门控结果通过 API `metadata.dq_status` 返回
- 前端展示 `DegradedBanner` 警告条

#### 4. 跨平台商品匹配（Matching）

**FR-4.1 多阶段候选召回**
- 第一阶段：品牌 + 品类阻隔（缩减 O(n²) 比较）
- 第二阶段：TF-IDF 文本相似度预过滤
- 第三阶段（可选）：OpenSearch BM25 全文检索
- 第四阶段（可选）：向量召回（FAISS/Milvus）

**FR-4.2 多信号加权打分**
- 品牌相似度（权重 30%）、规格匹配度（25%）、标题相似度（30%）、价格接近度（15%）
- 综合分数范围 [0.0, 1.0]

**FR-4.3 分类与自动化**
- 自动接受：≥ 0.85 → `exact_same` 或 `variant_family`
- 需要审核：0.65–0.85 → 人工决策
- 自动拒绝：< 0.65 → `no_match`

**FR-4.4 人工审核工作流**
- 通过 API `/review/{tiktokId}/{shopeeId}/decision` 提交决策
- 支持 accept、reject、change_type 三种操作
- 所有决策记录审计日志

#### 5. 告警与异常检测（Alerting）

**FR-5.1 四种告警类型**
- `rank_jump`：排名连续运行间变化 ≥ 50 位
- `proxy_spike`：销售代理增长 > 50%（review_count / likes / sold）
- `price_anomaly`：价格为零、负数、或 > 3x / < 0.2x 品类中位数
- `platform_gap`：品牌在一个平台进入 top-50 但在另一个平台缺失 / 排名 > 150

**FR-5.2 告警生命周期**
- 状态流：`open` → `acknowledged` → `resolved` / `dismissed`
- 通过 API `/alerts` 查看和管理
- 支持按类型、严重级别、状态筛选

#### 6. API 服务（Service Layer）

**FR-6.1 9 个 REST 端点**
- `/healthz` — 健康检查
- `/overview` — 仪表盘 KPI（聚合统计）
- `/top-items` — 分页商品列表（支持多种筛选）
- `/items/{platform}/{itemId}` — 单商品详情（含价格/销售代理历史）
- `/alerts` — 分页告警列表
- `/review-queue` — 待审核匹配队列
- `POST /review/{tiktokId}/{shopeeId}/decision` — 提交审核决策
- `GET/POST /our-mapping/{platform}/{itemId}` — 内部 SKU 映射 CRUD

**FR-6.2 分页与过滤**
- 偏移量分页（`limit` + `offset`）
- 支持多维筛选：平台、品类、品牌、价格范围、匹配状态、排序
- 默认 limit=20，最大 limit=100

**FR-6.3 幂等性与审计**
- `Idempotency-Key` 请求头防止重复写
- AuditService 记录所有写操作（谁/何时/旧值/新值/备注）
- `X-Request-Id` 关联 ID 支持追踪

**FR-6.4 认证与授权**
- 本地开发：无认证（`VITE_AUTH_DISABLED=true`）
- 生产环境：Keycloak OIDC + JWT Bearer + RBAC
- 三级角色：VIEWER（只读）/ REVIEWER（审核权限）/ ADMIN（管理权限）

**FR-6.5 限流**
- 固定窗口限流：100 请求/分钟/IP
- 429 响应 + `Retry-After` 头

#### 7. 前端展示（UI）

**FR-7.1 Web 前端（React SPA）**
- 5 个主要页面：概览、畅销商品、商品详情、告警、审核队列
- OIDC+PKCE 登录流程（本地开发跳过）
- ErrorBoundary + Sentry 错误上报
- 支持数据新鲜度降级警告

**FR-7.2 Streamlit 演示应用**
- 5 个页面：概览、畅销商品、告警、审核、运行流水线
- 直接读取 DuckDB，支持 API POST 提交决策
- 快速原型，零构建

### 非功能性需求（NFR）

| 需求 | 目标 | 说明 |
|-----|------|-----|
| **TopN 覆盖率** | ≥ 95% | 成功采集的商品数 / 期望数量 |
| **跨平台匹配率** | ≥ 60% | 有效匹配的商品对 / 总商品对 |
| **流水线成功率** | ≥ 99% 天数 | 每月自动运行无需人工干预的天数 |
| **API 响应时间** | < 2s（p95） | 包括网络延迟 |
| **数据新鲜度** | < 2h | 计划运行到数据可用的时间 |
| **可用性** | 99% 上线时间 | 本地开发不适用，生产目标 |

## 超出 MVP 范围的已实现功能

在实现过程中，以下功能原定为"非目标"，但因其核心价值而被实现：

| 功能 | 理由 | 实现状态 |
|-----|------|--------|
| **告警** | 自动异常检测对竞争情报用例至关重要 | ✅ 4 种告警类型 |
| **内部 SKU 映射** | 追踪自有商品覆盖的能力必不可少 | ✅ 完整 CRUD + 审计 |
| **数据质量状态传播** | 前端需要可见性 | ✅ DegradedBanner |
| **OIDC/JWT 认证 + RBAC** | 生产环境安全基线 | ✅ Keycloak + Spring Security |
| **API 限流** | 防止滥用和 DoS | ✅ 100 req/min/IP |
| **可观测性** | 错误追踪和事件分析 | ✅ ErrorBoundary + Sentry |
| **标准化缓存** | 性能优化，减少重复计算 | ✅ LRU 缓存 |
| **高级召回策略** | 覆盖率优化 | ✅ OpenSearch + 向量召回 |
| **安全基线** | 代码质量 | ✅ secrets 检测 + SCA |
| **OpenAPI 破坏性变更检测** | API 契约保护 | ✅ oasdiff CI |

## 明确排除范围

以下功能仍有意排除在 MVP 之外：

1. **全文搜索** — 无跨商品列表的自由文本搜索
2. **实时数据** — 仅支持每日批处理
3. **社交媒体集成** — 仅电商平台数据
4. **多国支持** — 仅泰国（无多国路由、货币转换）
5. **导出/报告** — 无 CSV/PDF 导出
6. **历史回填** — 仅从启动日期开始收集

## 约定与标准

### 数据标准

- **日期格式**: ISO 8601 (`YYYY-MM-DD`)
- **时区**: 内部 UTC，显示转换为 `Asia/Bangkok`
- **货币**: THB，存储为 satang（整数）
- **字段名**: `snake_case`
- **ID 格式**: 平台原生 ID（Shopee: `s_xxxxx`；TikTok: `tt_xxxxx`）

### 版本管理

- Schema、规则、API 遵循语义化版本（MAJOR.MINOR.PATCH）
- 见 `versioning/version-strategy.md`

### 变更流程

- 新增 SQL 列（可空）= 次版本升级（向后兼容）
- 修改列类型 / 删除列 = 主版本升级（破坏性）
- API 端点变更需通过 oasdiff 检测
